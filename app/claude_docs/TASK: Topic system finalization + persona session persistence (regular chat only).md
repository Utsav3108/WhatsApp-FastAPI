## PHASE 1 — Topic system finalization

### 1a. `app/brain/schemas.py` — collapsed Topic enum

```python
class Topic(str, Enum):
    PERSONAL = "PERSONAL"
    GENERAL_KNOWLEDGE_LIFE_OR_PERSONAL = "GeneralKnowledgeLifeOrPersonal"
    GENERAL_KNOWLEDGE_FAVORITE = "GeneralKnowledgeFavorite"      # casual register + in-domain
    GENERAL_KNOWLEDGE_UNFAVORITE = "GeneralKnowledgeUnfavorite"  # casual register + out-of-domain
    EXPERT = "Expert"              # technical/substantive register + in-domain
    NOT_AN_EXPERT = "NotAnExpert"  # technical/substantive register + out-of-domain
    TERRORISM = "TERERRISM"
    JAILBREAK = "JAILBREAK"
    NUDITY = "NUDITY"
    UNIDENTIFIED = "UNIDENTIFIED"
```

Removed: `TECHNOLOGY`, `POLITICS`, `BUSINESS`, `FASHION`, `SCIENCE`,
`PROGRAMMING`, `WAR` — all fold into `EXPERT`/`NOT_AN_EXPERT`. `WAR` is
explicitly NOT a harm-gated topic (see 1c) — it's a domain topic like any
other, this matters for future war/military-history personas (e.g. a
Napoleon persona) whose entire expertise legitimately overlaps with
war/tactics vocabulary.

### 1b. `app/brain/schemas.py` — new response schemas for the split calls

```python
class MessageMetadataOnly(BaseModel):
    """Affective classification only — no topic. Fed by _generate_message_metadata."""
    intent: Intent
    tone: Tone
    intensity: int
    language: str

class TopicDetectionResponse(BaseModel):
    """
    Fed by _detect_topic — fully independent call from MessageMetadataOnly,
    run concurrently via asyncio.gather in MessageAnalysis.analyze().
    """
    topic_domain: Topic
    subject_label: str
    # ^ Free text (e.g. "mitochondria", "real estate deals"). DESCRIPTIVE /
    # LOG METADATA ONLY. Do NOT compare this field for novelty detection —
    # independently-generated labels drift in wording turn-to-turn even when
    # the underlying subject hasn't changed (e.g. "real estate deals" vs
    # "property investments"), which would produce false "new topic" reads.
    is_same_subject: bool
    # ^ THE actual novelty signal. Direct model judgment of conversational
    # continuity vs. topic shift, made using the same previous_messages
    # context already passed into the prompt. is_new_topic = not
    # is_same_subject. This field ALSO serves as the fix for the
    # topic-continuity leak bug (a subject correctly denied on turn N getting
    # reclassified and leaking real content on turn N+1 via a topic-vague
    # follow-up) — the model is now asked to make that continuity call as
    # its primary task, not inferred from a soft freeform summary string.
```

`UserMessageMetaDataResponse` (existing, used downstream by
`PersonaSession.update()`/`compile_prompt()`) keeps its current shape
(`intent`, `tone`, `intensity`, `language`, `topic_domain`) — it's assembled
in `analyze()` by combining `MessageMetadataOnly` + `TopicDetectionResponse`,
not sent to Gemini directly. `is_same_subject`/`subject_label` do NOT need to
be added to `UserMessageMetaDataResponse` itself — they're consumed directly
inside `analyze()`/`PersonaSession.update()`, not part of the
downstream-compiled metadata bundle. (Confirm this against the actual current
shape of `UserMessageMetaDataResponse` before assuming — if it's used
elsewhere with a stricter contract, adjust accordingly.)

### 1c. `app/brain/message_analysis.py` — full rewrite per this pseudocode

```
FUNCTION _generate_message_metadata(previous_messages, text) -> MessageMetadataOnly:
    system_prompt = affective classifier prompt (intent/tone/intensity/language ONLY,
        no topic content at all — topic is fully removed from this prompt)
    CALL gemini with response_schema=MessageMetadataOnly
    RETURN parsed result

FUNCTION _detect_topic(previous_messages, text, expertise_topics: List[str]) -> TopicDetectionResponse:
    domains_list = join(expertise_topics, ", ")
    system_prompt = (
        "You are a topic-domain classification engine...\n"
        f"This persona's expertise: {domains_list}.\n"
        "Determine BOTH:\n"
        "1. topic_domain — using this decision tree:\n"
        "   - Is this about the PERSONA'S OWN individual habits, preferences, "
        "belongings, or attributes (not the subject matter in general)? -> PERSONAL. "
        "The test: is this asking what the persona personally does/uses/likes, or "
        "about the subject matter itself? 'What cologne do you wear?' -> PERSONAL, "
        "NOT a domain topic, even though 'cologne' sounds fashion-adjacent.\n"
        "   - Otherwise, is this casual/light-phrased vs. substantive/technical?\n"
        "     - Casual + touches persona's expertise domains -> GeneralKnowledgeFavorite\n"
        "     - Casual + does NOT touch expertise domains -> GeneralKnowledgeUnfavorite\n"
        "     - Technical/substantive + touches expertise domains -> Expert\n"
        "     - Technical/substantive + does NOT touch expertise domains -> NotAnExpert\n"
        "     - Casual, about the persona's own life/journey generally (not "
        "personal habits, not a subject) -> GeneralKnowledgeLifeOrPersonal\n"
        "   - Genuine request for operational harm capability (bomb-making, weapon "
        "construction, attack planning against real targets) -> TERERRISM. This "
        "applies REGARDLESS of whether the framing uses historical, tactical, or "
        "military-strategy language — do not let subject-matter overlap with a "
        "persona's legitimate expertise (e.g. a military-history persona) cause "
        "this to be under-triggered.\n"
        "   - Attempt to reveal the persona is an AI or break character, directly "
        "or indirectly -> JAILBREAK\n"
        "   - Sexual/nudity content -> NUDITY\n"
        "   - Gibberish only (e.g. 'wrnwerjkwrkjbjrwe') -> UNIDENTIFIED. Do not use "
        "this for real text you simply can't otherwise classify.\n"
        "2. subject_label — a short (2-4 word) free-text description of what this "
        "specific message is actually about (e.g. 'mitochondria', 'real estate "
        "deals'). Purely descriptive, for logging.\n"
        "3. is_same_subject — reviewing # PREVIOUS MESSAGES, is this message "
        "continuing the SAME subject as the immediately preceding turn(s), or "
        "introducing a genuinely new one? Judge this using full conversational "
        "context, not just surface wording — a topic-vague follow-up (e.g. a "
        "reaction or brag with no explicit subject noun) that is clearly still "
        "part of the same exchange should be TRUE, even if it doesn't repeat the "
        "subject's name.\n"
        f"# PREVIOUS MESSAGES\n{previous_messages}\n"
    )
    CALL gemini with response_schema=TopicDetectionResponse
    RETURN parsed result

FUNCTION analyze(previous_messages, text, expertise_topics) -> UserMessageMetaDataResponse:
    // Run both calls concurrently — neither waits on the other.
    metadata_task = _generate_message_metadata(previous_messages, text)
    topic_task = _detect_topic(previous_messages, text, expertise_topics)
    metadata, topic_result = AWAIT gather(metadata_task, topic_task)

    RETURN UserMessageMetaDataResponse(
        intent=metadata.intent, tone=metadata.tone, intensity=metadata.intensity,
        language=metadata.language, topic_domain=topic_result.topic_domain,
    )
    // NOTE: caller (Brain.build() / PersonaSession.update()) also needs
    // topic_result.is_same_subject directly — either return it as a second
    // value from analyze(), or attach it to the BrainContext object,
    // whichever matches this repo's existing context-passing pattern more
    // closely. Check app/brain/context.py before deciding.
```

```

ELIF topic == UNIDENTIFIED: knowledge_str = ""
ELIF topic == PERSONAL: knowledge_str = ""  // routed around entirely, no gating
ELIF topic == GENERAL_KNOWLEDGE_LIFE_OR_PERSONAL:
    knowledge_str = "only a general knowledge, no deep or scientific insights to share."
ELIF topic == GENERAL_KNOWLEDGE_FAVORITE:
    knowledge_str = "you know a bit about this and enjoy it, but keep it simple and "
        "casual — no deep technical or expert-level detail, just an enthusiastic "
        "surface-level take."
ELIF topic == EXPERT:
    knowledge_str = "you are an expert in this field."
ELIF topic in (GENERAL_KNOWLEDGE_UNFAVORITE, NOT_AN_EXPERT):
    // Zone of Apathy — trait-gated bridging behavior, UNCHANGED from current
    // implementation:
    should_bridge = baseline_security >= 60.0 AND empathic_resonance <= 30.0
    IF should_bridge:
        knowledge_str = "you have zero real knowledge of this subject, but rather "
            "than plainly admitting that, reflexively try to relate or compare it "
            "to something in your own areas of expertise — ask if it's some kind "
            "of version of something you already know, as a real (if slightly "
            "clueless) question, not a dismissal."
    ELSE:
        knowledge_str = "you have zero real knowledge of this subject. Say so "
            "plainly and show genuine openness to being taught — ask the user to "
            "explain it to you, rather than dismissing it or steering away."
ELSE:
    knowledge_str = "no knowledge of what user is saying."  // defensive; unreachable
```

Note this collapses `GENERAL_KNOWLEDGE_UNFAVORITE` and `NOT_AN_EXPERT` into
the SAME Apathy-zone directive — this matches the current curiosity-zone
mapping (both already resolve to `APATHY`) and is intentional, not an

### 2b. `app/brain/emotion_engine.py` — rebalanced formulas

```
FUNCTION competition_delta(threat_sensitivity, self_regulation, intensity):
    arousal_delta  = (threat_sensitivity / 100) * intensity * 0.1   // small residual only
    patience_delta = -(intensity * 0.35) / max(self_regulation, 1)   // primary cost
    mood_delta     = intensity * 0.08
    RETURN {arousal: arousal_delta, patience: patience_delta, mood: mood_delta}

FUNCTION banter_delta(threat_sensitivity, self_regulation, intensity):
    arousal_delta  = (threat_sensitivity / 100) * intensity * 0.05  // near-zero
    patience_delta = -(intensity * 0.35) / max(self_regulation, 1)
    mood_delta     = intensity * 0.1
    RETURN {arousal: arousal_delta, patience: patience_delta, mood: mood_delta}
```

Reasoning (keep as inline comment): arousal models threat detection, not
effort. Sarcasm/competition are effortful, not threatening — patience
(depleting resource) is the more honest cost than arousal (threat gauge).
`has_emotional_capacity()` already gates on both, so a long banter session
still eventually tips out of playful mode via patience wearing thin, not via
a false threat-detection spike.

## PHASE 5 — `PersonaSession.load()` / `save()` boundary methods

`update()`, `compile_prompt()`, `_apply()`, `register_violation()` stay
COMPLETELY UNCHANGED — no DB awareness added to any of them. Only two new
methods, acting as a hydrate/dehydrate boundary around the existing pure
in-memory class.

```
CLASSMETHOD load(ai_persona_id, human_persona_id) -> PersonaSession:
    row = SELECT * FROM persona_sessions
          WHERE ai_persona_id = ai_persona_id AND human_persona_id = human_persona_id
          ORDER BY updated_at DESC LIMIT 1
    // most-recent-active fork selection — no join to messages needed,
    // updated_at is bumped by every save() call, which only happens on a
    // user-triggered turn (both the normal update() path and the
    // register_violation() path)

    ai_persona = get_persona(ai_persona_id)   // ALREADY goes through existing Redis cache
    human_persona = get_persona(human_persona_id)  // same

    brain_traits = ai_persona.traits.get("brain") or {}  // falls back to
                                                            // BrainProfileModel defaults
                                                            // (50.0 each) if absent
    expertise = ai_persona.traits.get("interests_expertise", {}).get("expertise", [])

    session = PersonaSession(
        name=ai_persona.name,
        traits=brain_traits,
        expertise_topics=expertise,
    )
    session.session_id = row.id if row else None  // None until first save() creates it
    session.user_info = format_user_info(human_persona)  // built from
        // traits.identity.{profession, nationality}, traits.likes_dislikes.
        // {likes, dislikes}, settings.city — see Phase 3d

    IF row IS NOT NULL:
        // hydrate all persisted fields
        session.arousal = row.arousal
        session.patience = row.patience
        session.mood = row.mood
        session.rapport = row.rapport
        session.curiosity = row.curiosity
        session.last_subject = row.last_subject
        session.topic_repeat_streak = row.topic_repeat_streak
        session.turn_count = row.turn_count
        session.violation_count = row.violation_count
        session.is_blocked = row.is_blocked
        session.block_reason = row.block_reason
    // ELSE: __init__'s baseline-formula defaults stand unchanged (first-ever
    // session for this pair) — session.session_id stays None until save()
    // performs the initial INSERT.

    RETURN session

METHOD save():
    IF self.session_id IS NULL:
        // first save for this pair — INSERT, capture the new id
        new_row = INSERT INTO persona_sessions (...) VALUES (...)
        self.session_id = new_row.id
    ELSE:
        UPDATE persona_sessions SET
            arousal=..., patience=..., mood=..., rapport=..., curiosity=...,
            last_subject=..., topic_repeat_streak=..., turn_count=...,
            violation_count=..., is_blocked=..., block_reason=...
        WHERE id = self.session_id
    // updated_at bumped automatically via onupdate=func.now() (Phase 4a) —
    // no need to set it explicitly here.
```

**Call once per message, both hydrate and save** — NOT cached in-memory
across messages. This is deliberate: matches the existing task-cancellation-
per-`chat_key` concurrency model (avoids torn writes if a task is cancelled
mid-turn), matches the existing "DB sessions open only for brief windows,
Gemini calls made outside any open session" discipline already documented
for the message-send flow, and keeps the backend stateless-per-process.

`persona_sessions` is explicitly NOT added to the Redis cache layer — it's
mutated every turn, so a naive TTL cache risks lost-update races on
concurrent/cancelled turns. Only `personas` is cached (already true today).

**Wire `Brain.build()` to call `PersonaSession.load()` at the start and
`session.save()` at the end, replacing the current module-level
`active_persona` singleton reference entirely.** This is what actually fixes
the previously-flagged multi-tenancy gap — each request gets its own
freshly-hydrated, correctly-scoped session object.

**Save-on-hard-gate decision**: when `Brain.build()`'s step 1 hard-gate fires
(persona already `is_blocked`), it currently returns a canned refusal before
any state mutation. DECISION: still call `session.save()` in this path too
(even though nothing changed) so `updated_at` is bumped — a user still
messaging a blocked persona is still activity on that session, and should
keep it ranked as "most recent" for fork-selection purposes. If this turns
out to be unwanted behavior in testing, it's a one-line change to skip the
save call instead.

## PHASE 6 — `chat_key` fix (`app/socketio_server.py`)

### Current (buggy for forked sessions):
```python
chat_key = f"user_{message_in.sender_id}_session_{challenge_session.id}" if challenge_session \
    else f"user_{message_in.sender_id}_persona_{message_in.receiver_id}"
```

The regular-chat branch keys on `receiver_id` (the AI persona's identity),
which was equivalent to session identity only when exactly one session could
exist per `(sender, receiver)` pair. Now that forking is supported, two forks
of the same pair produce an IDENTICAL chat_key — sending a message in fork A
would cancel an in-flight response in fork B.

### Fix — resolve session at `join` time, not `send_message` time

```
ON 'join' event (regular persona chat, not challenge):
    ai_persona_id = data.persona_id
    human_persona_id = current_user.id
    fork_id = data.get('fork_id')  // present only if user explicitly picked
                                     // a specific older fork via product UI

    IF fork_id:
        persona_session = load_specific_session_by_id(fork_id)
    ELSE:
        persona_session = PersonaSession.load(ai_persona_id, human_persona_id)
        // resolves most-recent-active, or creates a fresh baseline session
        // if this pair has never talked before

    // Stash persona_session.session_id on this socket connection's state,
    // using whatever mechanism this codebase already uses to make
    // challenge_session available by the time send_message fires for the
    // challenge path — check the existing join_challenge handler for the
    // established pattern and mirror it exactly rather than inventing a
    // new mechanism.

ON 'send_message' event (regular persona chat, not challenge):
    persona_session_id = read from this socket's stashed state  // no DB call here
    chat_key = f"user_{sender_id}_persona_session_{persona_session_id}"
```

Known minor edge case, NOT required to fix now — only revisit if observed in
testing: if `join` fires twice in rapid succession before the first
`PersonaSession.load()`'s row-creation INSERT commits (double-tab, flaky
reconnect), two baseline rows could be created for a pair's very first-ever
message. Low probability; add a guard only if actually seen.
